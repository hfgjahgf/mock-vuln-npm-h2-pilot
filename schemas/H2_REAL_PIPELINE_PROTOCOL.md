## 1. 这一轮问什么, 以及它**不**回答什么

H1、H2、R36 **全部是离线的**。R36 说"换成建议的那个版本, 模型里仍有区间命中它",
那是**对冻结语料的预测**, 不是对真实扫描器行为的观察。

**R37 只问三件事**, 且**分三个层级, 不并列**:

| 层级 | 问题 |
|---|---|
| **前置方法门** | **检测保真度**: 修复**之前**, 真实扫描器有没有检测到目标公告 |
| **主端点** | **应用修复后重扫**: 目标公告是否消失; 是否仍有其它公告残留 |
| **次端点** | **修复可施行性**: 依赖能否解析、lockfile 是否有效、`npm ci` 是否通过 |

**方法门不过 → 记 `not_detected_at_baseline`, 该环境的主端点结论作废。**
**不得假装执行过修复验证。**

### 1.1 R37 **不**回答的(措辞冻结)

- **不取代 H2 主推断。** 真实数据库是**运行当天**的状态, 不是 `snapshot_T = 2026-07-12`,
  两者是**不同总体**。`h2_supported = false` 与 R36 的全部数字**一律不动**。
- **不宣称测量了修复速度。** 本轮不测 MTTR、不测公告发布到修复可用的时延。
- **不外推到传递依赖。** 见 §3 的实验单位与它的代价。

### 2.1 一处**必须披露**的不对称(建议的来源不同)

| 臂 | 建议来自 | 时点 |
|---|---|---|
| GHSA / OSV | **活的公告库**(运行当天) | **运行日** |
| Unified | **冻结模型**(`snapshot_T = 2026-07-12`) | **冻结日** |

**Unified 的建议不是"活"的** —— 它是冻结模型的确定性回答, 只是**在真实环境里被执行**。
因此:

- **Unified 看不到 `snapshot_T` 之后新发布的公告与修复**, 而两个真实工具看得到。
- **方向事前不可知(R37c 更正)。** 上一版断言"这个方向对 Unified 不利"——**那不成立**:
  活库新增的公告同样会让**活臂**去尝试一个更高的修复版本, 而那个版本可能装不上、
  可能引入新的残留; 被撤回的公告则会让活臂**不再**动作而 Unified 仍然动作。
  **两个方向都存在, 净效应只能逐条看。**
- 因此: **任何一臂的优劣差异, 都必须先按 §8 归类**, 确认不是 `live_db_drift`,
  才谈得上归因于模型或工具本身。

**真正"活"的部分是: 安装、依赖解析、以及两个真实扫描器的重扫。**
**这三件事对三个臂完全一致**, 那才是本轮的对照所在。

### 2.2 Unified 臂**只读冻结清单**, 运行时不做任何判断(R37b-P0)

Unified 的建议**只能**来自 `schemas/H2_UNIFIED_RECOMMENDATIONS.json`
(由 `build_h2_unified_recommendations.py` 从 `h2_cicd_decisions.json` 生成, 带哈希)。

> **上一版让流水线自己重算 Unified** —— 把各源声明的全部修复合并后**按字符串排序取第一个**,
> 绕过了 H2 的成功门(可解析 / 快照当日可安装 / 可追溯 / 唯一)与 R36 的冲突判据。
> 实测后果: **27 个环境**冻结模型根本没有有效建议, 脚本却仍给出一个版本;
> **另有 6 个环境**给出的版本**不在**有效建议集合内。
> **那不是在测 Unified 模型, 是在测一个字符串排序。**

**清单里每个不同的建议版本各自安装并重扫一次**, 不发明任何"合并规则"。
实测冻结数据: **1,383** 个环境只有 1 个不同建议, **8** 个有 2 个 ——
逐个安装总共只多 **8** 次 phase-2, 而 per-query 归因完整保留。

## 3. 实验单位 = **顶层直接依赖**(R36a 裁决, 事先写死代价)

每个 fixture **只有一个目标包实例**, 作为**顶层直接依赖**安装。

- **忠实于冻结账本**: 账本的 `installed_version` 就是该包自己的版本,
  **依赖路径是冻结模型里根本没有的信息**。
- **代价一(必须写进效度限制)**: 顶层单依赖**几乎不会触发 peer dependency 冲突**,
  而真实痛点在**传递依赖被父包钉死**。
  **R37 的可施行性结论只覆盖顶层直接依赖, 不得外推为"npm 修复普遍装得上"。**
- **代价二**: **R36 的 `conflict = 0` 在 R37 里同样不会被真实依赖树检验** ——
  一个 fixture 一个实例, 不存在同包多版本共存。**这一格照实说空着。**

## 4. 两阶段全量普查(**不抽样**)

- **阶段一**: 对全部 **1,556** 个唯一 `(package, installed_version)` 环境做**修复前扫描**。
- **阶段二**: 对**每个臂在真实运行中实际产生可执行建议**的所有环境,
  执行修复 → 安装 → 重扫。
  > **建议取自真实运行的工具输出**(`npm audit` 的 `fixAvailable`、`osv-scanner` 的输出、
  > 我们 Action 的输出), **不是 R36 的预测**。R36 的预测只在事后比对时使用。
- 结果**映射回全部 2,927 条查询**。
- **无建议的环境记 `no_action_generated`, 不静默排除。**
- 账本的 **139** 条端点前 `skipped` **继续单列**, 不进任何分母。
- **不设每包上限**: `openclaw` 全部保留, 同时报告**排除它**的敏感性。
- **资源不足用分片 / batch, 不通过抽样缩小研究对象。**

> **构造上的便利**: **333** 个环境同时挂着多条查询, 真实扫描器扫一个 lockfile

## 5. 判据

### 5.1 前置方法门 —— 检测保真度

修复前的两个扫描器输出中, 是否出现该查询的**目标公告标识符**
(实体的 CVE、以及各源的原生 id, 由 `H2_REAL_ENVIRONMENTS.json` 事先列出)。

#### 5.1a 什么算"扫描器报出了这个标识符"(R37f-P0)

**只有扫描器自己声称的身份才算。** 逐工具:

| 工具 | 算身份 | **不算身份** |
|---|---|---|
| `npm audit` | `via[].url` 里的公告 id、`via[].cve[]`、`via[].aliases[]` | **`via[].title`**、`via[].source`、`via[].name` |
| `osv-scanner` | `vulnerabilities[].id`、`vulnerabilities[].aliases[]` | **`vulnerabilities[].related[]`** |

**公告标题是散文, 而散文会引用别的公告。** 实测(R37e 预检):
`GHSA-8gc5-j5rx-235r` 的标题是"…(**incomplete fix for CVE-2026-26278**)", 而它自己的
`cve` 字段是 **null**;另有一条 `sharp` 公告标题写着"inherited vulnerabilities in
**libvips**: CVE-…, CVE-…"——那是原生 C 库的 CVE, **根本不是 npm 包公告**。
扫描标题会让 `fast-xml-parser@5.3.6` 上**已经清除**的目标公告看起来仍然存在
(39 次尝试中的 2 次), 而两个扫描器随即**因此且仅因此**给出相反结论。

**正确表述**: 目标公告**已清除**, 但出现了**另一条** incomplete-fix 公告 ——
这在 R36 的词汇里是 `cross_advisory_residual_exposure`, **不是"目标仍存在"**。

标题里的引用**必须记录, 但归入 `textual_reference` 字段**
(`detection.npm_audit_textual_references` 与逐查询的 `textual_reference_only`),
**永不参与匹配**。与 `related` 同理: **引用不是身份主张。**

> **为什么这样不会丢东西**: `npm audit` 把公告 id 放在 `via[].url` 里 ——
> 预检中**每一条** `via` 字典都是如此, 因此不读标题**不丢失任何合法身份**;
> `source` 与 `name` 一个标识符都不贡献。
>
> (逐条计数见 `Working_Logs/WORKLOG_2026-08-18-a.md` §二。
> **本协议不写预检的测量值** —— 预检结果按定义不计入, 也不是本文件钉住的冻结输入,
> 因此那些数字在这里既无法被门重算, 也不该由一份规则文件承担。)

**逐扫描器分别判定并分别记录**(R37b-P1):

| 字段 | 含义 |
|---|---|
| `npm_audit.matched` | `npm audit` 报出的标识符与目标集合的交集 |
| `osv_scanner.matched` | `osv-scanner` 报出的标识符与目标集合的交集 |
| `any_scanner` | **辅助性**并集, **只作展示, 不作判据** |

- 某扫描器检测到 → 该扫描器视角下进入主端点。
- **两个都未检测到 → `not_detected_at_baseline`**, **该查询的主端点结论作废并单列**。
- **一个检测到而另一个没有, 本身就是发现**, 必须能从产物里读出来。
- **扫描器没能运行 ≠ 没检出**: `matched` 记 **`null` 而非空表**,
  **这些行不进检测率分母, 也不进主端点分母**。

**扫描状态由三件事共同判定, 缺一不可(R37d-P0)**:

| 状态 | 判据 |
|---|---|
| `ok` | 退出码是该工具用于"扫描完成"的码, **且**输出可解析, **且**载荷形状是该工具成功时的形状 |
| `scanner_error` | 退出码不在允许集合内, 或进程根本没跑起来 |
| `no_scannable_packages` | **osv-scanner 专有**: 退出码 `128`, 表示没有可扫描的包 —— 既不是错误也不是干净 |
| `output_unparseable` | 解析不出, 或载荷不是成功形状(如 **npm audit 顶层带 `error` 对象**) |

- **`osv-scanner`**: `0` / `1` 才是完成的扫描(`1` = 发现漏洞); `127` 是通用错误,
  `128` 是"无可扫描的包"; 载荷必须有 `results` 列表。
- **`npm audit`**: `0` / `1` 才是完成的扫描; **顶层 `error` 对象即失败**
  —— 注册表调用失败时它照样退 `1` 并打印 JSON。

> 上一版只要"退出码不是 None 且能解析成 JSON"就判 `ok`。实测三个反例全被判成 `ok`:
> osv 退 `127` 带 JSON 错误对象、osv 退 `128` 带空 `results`、
> npm audit 退 `1` 带网络错误对象。**能解析 ≠ 扫成功了。**

> 上一版把两个扫描器的标识符合并成一个集合再比对 —— **那就取消了这条发现**,
> 也让"npm audit 漏了但 OSV 报了"这种情况无法与"两个都报了"区分。

### 5.2 主端点 —— 应用修复后重扫(**安装门必须先过**, R37b-P0)

**执行顺序不得颠倒**:

```
生成 lockfile(--save-exact, 并核验 package.json 真的是精确版本)
  → npm ci --ignore-scripts
  → npm ls --all --json:  退出码 == 0 且 JSON 可解析 且 problems 为空
  → 核验目标包与版本在树上
  → 才重扫
```

> **`npm ls` 会在树有问题时以非零码退出, 同时照样打印完整 JSON。**
> 上一版只判"JSON 解析得出", 于是**一棵坏树也能通过全部四项**(R37c-P0)。
> **能解析 ≠ 树是好的。**
>
> **`--save-exact` 同样是必须的**: 不加它, `npm install pkg@x.y.z` 可能按 `save-prefix`
> 存成 `^x.y.z`, 那么 fixture 就不再是账本所指的那个版本。

- 上述**任一步失败 → `remediation_not_installable`**, **该臂在该环境上没有主端点结论**,
  失败原因按 §5.3 分类单列。
- **只有全部通过, 才允许进入重扫。**
- **重扫之后写的标签是 `installed_and_rescanned`, 不是 `remediated`(R37d-P1)** ——
  runner 记录**它做了什么**, **不下"修好了"的判断**:
  重扫可能仍报出目标公告, 扫描器也可能失败。
  **是否真的修复, 由 ingest 逐扫描器判定。**

> 上一版**先重扫、后安装**, 且 `outcome` 无条件写成 `remediated` ——
> **一个根本装不上的修复会被记成"已修复并重扫过"**。
> 那不是次端点顺序问题, 那会直接污染主端点。

| 字段 | 含义 |
|---|---|
| **`post_scan_target_cleared`** | 目标公告在重扫中消失(**逐扫描器**) |
| **`post_scan_residual_exposure`** | 重扫仍报出该包的其它公告(**逐扫描器**) |

### 5.3 次端点 —— 修复可施行性(**不执行依赖代码**)

生成一致的 `package.json` / `package-lock.json` →
`npm ci --ignore-scripts --audit=false` 成功 →
`npm ls --all --json` 得到有效依赖树 → **核实目标包及版本出现在预期依赖路径**。

| 字段 | 含义 |
|---|---|
| **`lockfile_constructable`** | 能否解析出一致的 lockfile |
| **`dependency_resolution_pass`** | `npm ls` 是否给出有效树 |
| **`target_version_present`** | 目标包及版本是否在预期路径上 |
| **`install_pass_scripts_suppressed`** | `npm ci --ignore-scripts` 是否通过 |
| **`runtime_compatibility_not_tested`** | **恒为真的声明** —— 运行时兼容性本轮不测 |

**七个字段各自记录, 不得合成单一布尔。**

**不做通用 smoke import**, 理由事先写死:
`require()` 会误伤 ESM-only 包; 浏览器/CLI/无根导出的包本就不能通用 import;
import 本身会执行第三方代码, 与隔离原则冲突;
跳过 `postinstall` 之后, 原生模块 import 失败**不能归责于修复版本**。
**安装脚本被抑制、因而无法验证的原生模块单独标记。**

失败原因**单列**: `peer_dependency` / `version_not_found` / `transitive_constraint` /
`registry_error` / `other`。

### 5.3b 各臂的建议**如何从工具输出里取**(R37b-P1)

| 臂 | 取法 |
|---|---|
| `npm_registry_audit_live` | `fixAvailable` **有三态**, 见下 |
| `osv_scanner_live` | **逐目标公告 + 逐区间段绑定**, 见下 |
| `unified_frozen_model` | **只读 §2.2 的清单** |

**`npm audit` 的 `fixAvailable` 是三态, 不是两态(R37c-P0)**:

| 值 | 含义 | 处置 |
|---|---|---|
| `object` | 需要指定版本(可能是 major) | 取 `version`, 记 `isSemVerMajor` |
| **`true`** | **普通 `npm audit fix` 即可修复**, 但此处不给版本 | **修复的载体是那两份文件本身**, 见 §5.3c |
| `false` | 工具明说没有自动修复 | `tool_says_no_fix`, 视为该臂的**回答** |

> 上一版只处理 `object`, 于是 **`true` 被当成"没有建议"** —— 与"确实没有修复"无法区分。
> **那会系统性地少算 npm 臂的动作。**
>
> **`--package-lock-only` 是必须的(R37d-P0)**: 修复以 lockfile-only 方式施加, 此时
> **没有 `node_modules`**, 普通 `npm ls` 会报 `missing` 并退 1, 读不到任何版本 ——
> 该分支因此**必然**落回"无建议"。在钉定的 Node 22.20.0 / npm 10.9.3 上实测:
> `npm ls --all --json` 退 1、版本为空; `npm ls --package-lock-only --all --json` 退 0、
> 版本正确。

#### 5.3c `fixAvailable: true` 的建议**是一棵树, 不是一个版本号**(R37f-P0)

npm 对 `npm audit fix` 的定义是**对整棵依赖树施加修复**;在 `--package-lock-only` 下,
它改写的对象就是 **`package-lock.json`**(以及可能被放宽的 `package.json`)。

因此:

1. **修复产物 = 那两份文件的内容**, 逐字保存(`lockfile` / `manifest` + `lockfile_sha256`);
2. **`attempt()` 必须把这两份文件原样放回再装**, 由 `npm ci` 从这份 lockfile 安装。
   **不得**只留一个顶层版本号再用 `npm install <pkg>@<version>` 重建树 ——
   那会把 npm 做的**全部传递依赖改动**丢掉, 于是该臂**被评在一棵 npm 从未提议过的树上**;
3. **判据是"lockfile 有没有变", 不是退出码**。
   **`npm audit fix` 只要事后仍有漏洞就退 `1`**, 其中包含**成功的部分修复**;
   而它什么也修不了时会**原样留下 lockfile**。
   - **lockfile 未变 → `audit_fix_changed_nothing` → 该臂 `no_action_generated`**;
   - **lockfile 变了 → 有修复动作**(哪怕只修了一部分), 按上面第 2 条安装并重扫;
   - **`npm audit fix` 根本没跑起来(退出码为空 / 超时)→
     `remediation_action_not_executable`, 单列并排除, 不进任何分母(R37g)。**
     **那是我们没问成, 不是 npm 拒绝动作** —— 与 §5.1 "扫描器没能运行 ≠ 没检出"同条纪律。
     大依赖树上 `npm audit fix` 是有可能超时的, 把超时记成 `no_action_generated`
     会**把我们自己的失败记进 npm 那一栏**。
4. 顶层版本仍然记录(`top_level_version`), 但它是**报告字段**;
   安装门的 `target_version_present` 照常判定, **不得因为"载体是 lockfile"就置真** ——
   `npm ci` 装的就是这份 lockfile, 那一步是**可评估的**。

> 反例已复现: `npm audit fix` 退 `1` 且 lockfile 未被改写, 旧实现从那份**未改动**的
> lockfile 里读出 **`1.0.0`**(即安装版本)并当作建议返回 ——
> **一次失败的修复被记成了一条建议**, 随后"安装"一个空操作再重扫, 漏洞自然还在,
> 于是该臂被记成"给了建议但没修好", 而真相是**它根本没有产生动作**。
>
> 这与 §5.2 的 `installed_and_rescanned` 是同一条纪律: **runner 记录它做了什么。**
> 而"做了什么"的单位, 对 npm 而言就是**它写下的那棵树**。

**这条路径在本队列里预期不可达, 这是 §3 单位选择的后果(R37g)。**
`fixAvailable: true` 的语义是"**不改你声明的东西**就能修好";而 §3 规定每个 fixture
只有**一个精确钉版的顶层直接依赖**, 且它之所以入组, 正是因为**有公告点名它自己** ——
修它必然要改它自己声明的版本, 于是 npm 只能给 `object` 形。

**实测**: 队列环境已探过一批, `true` **一次未出现**;而同一批 `npm audit` 报告里
`true` 大量出现, **全部落在传递依赖条目上**(那些包的漏洞在它们的依赖里)。
逐条计数见 `Working_Logs/` 中 R37g 那份日志。

**因此**:

- 该分支由单元门 `audit_fix_carries_a_lockfile` 覆盖, 并**另在队列之外用真实 npm 跑通过**
  (一个 `via` 为传递包名、装成顶层后仍答 `true` 的真实包;**结果不计入**, 它不是队列成员);
- **正式全量中若真的出现 `true`, 那本身就是一个发现** ——
  它意味着该包**自己的公告在活库里已不适用**, 而它的依赖有问题。
  **`Test_h2_real_run.py` 必须把这类记录单列并计数**, 不得让它悄悄走一条从未被真实数据
  走过的路径。

**OSV 取法(不得按字符串取第一个)**:

1. 在 `results[].packages[].vulnerabilities[]` 里, 找 `id` 或 `aliases`
   与该查询的**目标标识符集合**相交的那条漏洞;
2. **把该 `ranges[]` 的 `events` 展开成"段"**: 每个 `introduced` 开启一段,
   随后的终止事件闭合它 —— **一个 range 可以有多段**
   (`introduced → fixed → introduced → fixed`);
3. 找**安装版本所在的那一段**, 取**该段**的 `fixed`;
4. **终止事件必须区分**: 只有 **`fixed`** 是修复;
   **`last_affected` 与 `limit` 闭合区间但不给修复** —— 记 `segment_without_fix`, 不得当作修复;
   **且边界开闭不同(R37d-P1)**: `last_affected` 指"最后一个仍受影响的版本",
   故该段**闭区间** `<=`; `fixed` 与 `limit` 指"第一个不再受影响的版本", 故**开区间** `<`。
   > 三者一律用 `<` 会把**恰好落在 `last_affected` 上**的版本判成"不在自己的受影响段内"。
5. **区间类型必须区分**: `SEMVER` / `ECOSYSTEM`(npm 即 semver 序)可比;
   **`GIT` 存的是 commit 哈希, 与 npm 版本不可比** —— 记 `range_type_not_comparable`;
6. 用 semver 验证; 多个目标公告时取 **semver 最大**, **不是字典序**。

> 上一版把该包**全部漏洞**的**全部 `fixed` 事件**聚在一起再 `sorted()[0]`, 且
> **只保留最后一对 `introduced`/`fixed`** ——
> 构造 `[1.0.0,1.0.2)` 与 `[3.0.0,3.2.5)` 后, 装 1.0.1 **返回 `None`**,
> 一个存在的修复直接消失。

### 5.4 R37 的 semver 语义: **node-semver, 在运行时执行**

R36 用的是**离线冻结账本**(因为派生环境不得联网、不得调 Node)。
R37 的 runner 本来就有 Node, 且要判定**活库里出现的、账本里没有的版本**,
因此**直接调用 npm 自己的 `semver`**(版本随 Node 一并钉住)。

- **语义与冻结账本同源**(都是 npm `semver`), **只是执行地点不同** —— 必须写清这一点;
- **仍然不自己实现区间语义**;
- 判定不了(如版本串非法)→ 记 `semver_undecidable`, **不猜**。

## 6. 安全与隔离

- **`permissions: contents: read`**, **无 secrets**, 不使用可写令牌。
- **全程 `--ignore-scripts`** —— 不执行任意包的生命周期脚本。
- **不使用 `osv-scanner` 的 guided remediation**: 官方标注为实验性,
  且明确提示可能触发包管理器脚本。**修复由我们自己用
  `npm install <pkg>@<fix> --package-lock-only --ignore-scripts` 施加。**
- 每条记录必须捕获: `node --version` / `npm --version` / `osv-scanner --version` /
  OSV 数据库时间戳 / 运行的 UTC 时间。
- **`osv-scanner` 必须钉死版本号并校验 SHA-256**(R37b-P2)。
  上一版下载 `releases/latest` —— **那意味着两次运行可能用的不是同一个扫描器**,
  而这一轮的全部结论都建立在"扫描器行为"之上。
- **`node` 与 `npm` 版本钉死**; `npm` 由 Node 发行版带入, 一并记录。
- **另需逐次记录(R37c-P2)**: 所用 **npm registry**(`npm config get registry`)、
  **runner 镜像与版本**、**`semver` 包版本**。
- **每次扫描对应的 `package-lock.json` 与 `npm ls` 原始输出, 连同哈希一并保存** ——
  否则事后无法判断"扫的到底是哪棵树"。

## 7. 可复现性(**活库只跑一次, 回流即冻结**)

真实运行**不可能**逐字节复现 —— 活的公告库每天在变。因此:

**工作顺序不得颠倒(R37c-P1)**:

1. **修正 runner**;
2. **工程预检**(少量环境, **结果不计入**);
3. **用预检产物写完并测试 `ingest_h2_real_run.py` 与 `Test_h2_real_run.py`**;
4. **冻结 runner / ingest / gate 的哈希**;
5. **最后才跑唯一一次正式全量**。

> 若先跑全量再写 ingest, **等发现缺字段时, 那个活库时点已经过去了, 无法补救**。

1. **运行一次**, 原始扫描输出与运行元数据**全部回流**;
2. **必须保存能验证该哈希的原始 stdout 本身**(R37b-P2)——
   上一版只存了 `raw_sha256` 与解析结果, **那个哈希没有任何东西可以对照**,
   等于没有溯源;

   **原始输出的实际所在地是 Actions artifact, 保留期 90 天(R37f-P2 更正)。**
   上一版写着"留在**公开的流水线仓库**并按哈希钉住" —— **那不是事实**:
   artifact **不在仓库里**, 也**会过期**。**保留期不等于发表。**
   因此正式全量之后**必须在过期之前**把原始产物取出并归档,
   论文才可以引用它;在归档完成之前, **不得**称其为"公开的原始证据"。

   **两个哈希, 回答两个不同的问题(R37f-P2)**:

   | 字段 | 取自 | 用途 |
   |---|---|---|
   | `raw_sha256` | **存下来的文本** | 让原始包**自校验** —— 逐条重算必须相符 |
   | `stdout_bytes_sha256` | **进程真正写出的字节** | 证明那段文本确实来自该次运行 |
   | `decoding_lossy` | —— | 为真时存下的文本是**有损呈现**, 只有字节哈希能作证 |

   > `errors='replace'` 会改写非法 UTF-8, **对替换后的文本取哈希, 证明的是一个
   > 扫描器从未输出过的字符串**。解码无损时两个哈希相等, 这是常态;
   > 不相等时必须由 `decoding_lossy` 明说。

   **有损解码时必须把原始字节一并保存(R37g-P2)。** 只存"渲染后的文本 + 字节哈希"
   **等于让那个哈希无原件可算** —— **恰好在它唯一有存在意义的那种情形下不可复核**。
   故有损行必须带 **`content_b64`**(原始字节本身), 且
   **去重键改用字节哈希** —— 两串不同的字节可以解码成同一段替换后文本,
   只按文本去重会**静默丢掉第二串的原件**。

   **`Test_h2_real_run.py` 的门必须查这一条**: 凡 `decoding_lossy = true` 的记录,
   **要么带可解出且能重算出该字节哈希的 `content_b64`, 要么直接判失败**。
   **不得**只把它记成一个警告字段。

   **每次扫描还必须记录它自己的观测时点** `observed_utc` ——
   **osv-scanner v2 不报告数据库时间戳**, 所以"这次扫描问的是哪一天的活库"
   **只有扫描时刻能回答**。运行元数据另须记 `github_run_id` / `github_run_attempt` /
   `github_sha` / `github_ref` / 工作流输入 —— 否则分片文件**无法回指到产生它的那次运行**,
   两次跑不同代码的运行看起来一模一样。
3. **论文仓库入库归一化记录**(`.jsonl` —— `.gitignore` 挡 `*.jsonl.gz`);
4. **对这些回流数据的一切分析都是离线的、逐字节可复现的、由门守的。**

> 与 registry 快照、node-semver 账本同一类: **一次性外部夹具, 取回后即冻结。**

## 8. 与 R36 分歧时的处置(**事先定死**)

R36 **保留**为冻结语料上的离线预测; 真实扫描**不取代** H2 主推断。差异**逐条分类**:

| 分类 | 归属 |
|---|---|
| `live_db_drift` | 公告新增 / 修改 / 撤回 —— **外部有效性结果** |
| `tool_coverage_or_dedup` | 扫描器覆盖或把同一漏洞并成另一个 ID —— **工具行为差异** |
| `npm_resolution` | 真实依赖树装不上 —— **R36 简化模型的外部有效性限制** |
| **`implementation_error`** | **冻结输入 / 字段映射 / R36 实现错误** |

> **`implementation_error` 不得被本轮消化掉。** 任一条被归入该类 →
> **门 exit 1**, 本轮以"需开显式修正轮"收尾, 旧结果**保留**并就地作废。
> 这是唯一一条会让 R37 以未完成收尾的路径, **做成机器强制, 不靠自觉**。

**四句白话**(措辞冻结):
今天数据库新增公告 → 不是 R36 算错;
扫描器把同一漏洞并成另一种 ID → 工具行为差异;
npm 真实依赖树装不上 → R36 简化模型的外部有效性限制;
**R36 代码把一个区间判断错了 → 这是实现错误, 必须修正, 不能归入"外部限制"。**

### 9.1 回流摄取器与门的职责(R37h)

**runner 不下判断, ingest 才下判断**(§5.2)。因此三者的分工写死:

| 谁 | 做什么 | **不做什么** |
|---|---|---|
| `run_environment.py` | 记录它做了什么: 装了什么、扫了什么、工具说了什么 | **不判定"修好了"**, 不算任何比率 |
| `ingest_h2_real_run.py` | **离线**归一化 + 逐查询判定主端点 + §8 归类 + 计数 | **不联网**, **不修补 runner 记录**, 不决定 `h2_supported` |
| `Test_h2_real_run.py` | 独立复算并挡住 §9 的 25 件事 | **不导入生成器的常量** |

**run class 由运行自己记录的工作流输入派生, 不由任何人声明。**
`limit == 0` 且 `shards == all` → **`census`**;否则 **`engineering_precheck`**。
门对两者要求不同: 预检只需**对它被要求的范围完整**;
**`census` 另须覆盖全部 1,556 环境与 2,927 查询**。
**因此把预检改个标签当成全量, 会被门当场判失败** —— 这条不靠自觉。

**主端点是逐查询的。** 目标公告属于查询, 而一个环境可以挂多条查询、方法门逐条判定。
**方法门未过的那条查询没有主端点**(§5.1), 其判定记 `null` 并附
`voided_reason`, **不得记成"未清除"**。
**残留暴露属于包**(该包仍被报出的、不属于本环境任何目标的公告), 逐次尝试记一次。

**正式全量启动的前置条件(缺一不可)**:

1. `ingest_h2_real_run.py` 与 `Test_h2_real_run.py` **存在, 且在预检产物上 25 项全过**;
2. **`runner` / `ingest` / `gate` 三个内容哈希已冻结并入库**;
3. 协议版本与产物内记录的 `protocol_sha256` 一致。

> **一个版本号只能对应一份内容。** 协议内容一改, 版本号就必须动 ——
> 否则"按 `-5` 钉住"的产物与"改过的 `-5`"是两份不同的文件, 却共用一个名字。
