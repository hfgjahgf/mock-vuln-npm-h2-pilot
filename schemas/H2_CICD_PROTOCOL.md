## 1. 这一轮问的是哪一句

H2 问: **哪个臂能检索到一条可执行的修复。**
它**没有问**下一步 —— **如果换成它给出的那个版本, 这个包在模型里还会不会被命中。**

R36 只问这一句。**同一批冻结输入, 同一个单位, 同一个分母。**

> **诊室类比的下一格**: H1 是把三家医院的病历整理成一套可信档案; H2 是拿这套档案去诊室,
> 看医生能不能开出正确、可执行的处方。
> **R36 是在纸上算「换成这个药之后, 按病历上写的, 理论上还会命中哪些病症」**
> —— **药没有真的吃下去**。真的吃下去再复查一次, **那是 R37**。

## 2. 单位与分母 (**一律沿用, 不新建**)

- **单位** = 冻结账本里的一条查询, 即 `(entity_id, 规范化 npm 包)` 对。
- **分母** = 账本的 **2,927** 条查询。
- 账本的 **139** 条 `skipped` **仍然在端点之前排除**: 它们构造不出查询,
  **不进任何分母, 不计任何一类**, 单独报告。
- **`not_comparable` 沿用 H2 的处置**: 无 CVE 层的实体键为 `native:<source>:<id>`,
  其余单源臂**根本没有问题可答** → 该臂在该查询上**不产出类别**, 单独计数。
  它是资格事实, **不是第五类**。

> **R36 不得新建分母, 也不得改动任何 H2 分母。** 一旦分母变了,
> 本轮的数字就不再与 H2 的数字说同一批查询, 两者就不能并排读。

## 3. 重扫基线 (**主口径 = 该臂自己声明的区间**)

判定"装上之后是否仍受影响"时, 拿来重扫的区间集合是:

- **主口径**: **该臂自己**在整个账本中为**该包**声明过的全部受影响区间。
- **次要臂(并列报出, 不混算)**: **三源并集**为该包声明过的全部区间。

> **为什么主口径不是并集**: 不能因为一个源没有的公告去判它失败 ——
> 与 `h2-protocol-8` §4「单源臂只对**它自己**的建议负责」是同一条原则。
> 并集回答的是另一个问题("装完之后你到底还脆不脆弱"), 所以它并列报出而不是取代。

**"并列报出"是产物必须真的输出两套计数, 不是写一句话说它存在(R36a)。**
上一版只写了 `secondary_reported_separately` 这一个字符串, 没有对应数字;
门 `union_baseline` 现在**独立重算并比对**这两套读数。

**Unified 臂的知识 = 三源并集**, 因此它的主口径与次要口径重合 —— 这是定义使然,
**不是巧合, 也不得当成两次独立确认**。

## 4. 四个顶层类别 (**逐臂、逐查询;顺序即优先级**)

| 类别 | 判据 |
|---|---|
| **`undecidable`** | 该臂给不出可执行的修复 |
| **`conflict`** | 该臂给得出修复, 但它们无法同时成立 |
| **`post_remediation_exposure`** | 修复已装上, 但该臂自己的区间仍然命中它 |
| **`decided`** | 修复已装上, 且逃出该臂对该包声明的**每一个**区间 |

**判定按上表自上而下**: 先问"有没有", 再问"唯不唯一", 再问"装完干不干净"。

### 4.1 `undecidable` 的子类 (**沿用 H2 七分类的名字, 不另起炉灶**)

`not_covered` / `covered_but_no_package` / `package_but_no_fix` /
`untraceable_or_invalid`。

### 4.1b `declines_action` **不是 `undecidable` 的子类**(R36a 更正)

即 H2 的 `range_disagreement`: 该臂把安装版本放在它所有区间之外, 于是**决定不动作**。

**它是与 `not_comparable` 同级的独立处置**: `category = null`,
**不进四类中的任何一类, 不并入任何比率**, 单独计数。

> "我认为你没事"与"我不知道"是两回事: **前者做了决定, 只是可能做错了。**
> 上一版把它写成 `undecidable` 的子类, **那就是本节禁止的那种归并** ——
> 一句"不并入任何比率"配上一个"它是 undecidable 的子类", 实现只会照后者做。
> 实测 GHSA **5** 条 / NVD **1** 条; 方向不变, 但分母因此各减这么多。

### 4.2 `conflict` 的两个来源

1. **查询内**: 该臂对本查询的适用分支给出多于一个修复版本
   (Unified 另加: 各源之间互相矛盾) —— 即 H2 的 `ambiguous_or_conflicting`。
2. **包级(R36 新增)**: 同一个包上, 该臂跨多条公告声明的修复
   **无法由单一安装版本同时满足**。

   **操作化**: 取该臂为这个包**声明过修复**的那些区间, 问「它声明的修复版本里,
   有没有哪一个同时落在这些区间之外」。**没有 → `conflict`。**

   > **⚠ 这条判据说的不是 lockfile(R36a 更正)。** 上一版写着"lockfile 只能钉一个版本",
   > **那对一般 npm 依赖树是错的** —— npm 可以在不同嵌套路径上保留同一个包的多个版本
   > (官方 `npm dedupe` 文档就展示了这种重复树)。
   > 因此本判据**只是模型层面的**: `conflict = 0` 的正确读法是
   > **「存在一个包版本候选, 能清除模型中的相关区间」**,
   > **不得**写成「真实 lockfile 里没有冲突」。
   > 真实依赖树上的冲突要由**真实 Actions 运行**回答, 见 §10。

   - **参与判定的只有「已声明修复」的区间。** 一条**根本没给修复**的公告是
     **缺席的建议**, 不是**矛盾的建议** —— 它属于 `post_remediation_exposure`。
     (否则 OSV 的 `introduced: 0` 生成的 `>=0.0.0` 会把同包上每条查询都拖成冲突。)
   - **候选版本必须是 npm 认得的版本。** 非法版本串**谁都不满足**,
     于是在「逃出全部区间」这个测试下看起来最干净 —— 它必须先被排除。

### 4.3 `post_remediation_exposure` 的两个子类 (**必须分开**)

| 子类 | 含义 | 归责 |
|---|---|---|
| **`target_advisory_persists`** | 装完仍命中**本查询这条公告**的区间 | **建议本身可能有误** |
| **`cross_advisory_residual_exposure`** | 本条公告已解决, 但仍命中**同一个包上另一条**公告 | **不归责于原建议** |

> **不把"治好了感冒但仍有高血压"写成"感冒药开错了"。**
> 两者都让流水线的终态不干净, 但只有前者能说这条建议错了。

### 4.4 产物必须直接给出的重组量

`decided + cross_advisory_residual_exposure` = **「本查询这条公告已解决」**。

> 这个量是 R36 与 H2 之间的桥。**必须由产物直接写出**, 不能让读者自己去加 ——
> 需要读者动手算的数字, 迟早会被算错一次。

## 5. npm 版本语义 (**一律不自己实现**)

区间成员判定全部来自离线账本 `schemas/H2_RANGE_DECISIONS.json`
(由 `tools/h2_semver_oracle/` 用 Node + npm `semver` 一次性离线判完)。

**账本缺任何一次 `(版本, 区间)` 判定 → 硬失败 exit 1。**
**绝不把缺失当成"不在区间内"。**

> R30c 的教训: **一个没有东西可过滤的过滤器会静默返回空**, 而空集看起来最健康。
> 在这里, 把"没查到"读成"不受影响"会**系统性地夸大 `decided`**。

**R36 不生成新的 oracle 夹具**: 所需判定已全部在冻结账本内(由门 `oracle_coverage` 断言)。
**构建与派生不得联网。**

## 6. 报告层级与强制敏感性

- **主**: 查询级(2,927 条)。
- **次**: 包级 —— **按包名在全 cohort 上合并**, 一个包一行。
  **这不是一棵真实依赖树, 不得说成"更接近真实 lockfile 扫描"(R36b 更正)。**
  且它的分母是**该臂在该包上至少有一个可评估类别**的包数, 因此**逐臂不同**
  (只有 `not_comparable` / `declines_action` 的包不在其中);
  字段名必须写清这一点, 且**未入选的包要按处置单列**。
- **强制**: 语料中包的分布极不均匀, 最大的一个包占据相当份额。
  产物**必须**同时给出该包的份额与**排除该包**后的全部计数。

> **不做这一步, 结论就等于在描述一个包。**

## 10. 本轮**不能**证明的事(R36a 新增, 措辞已冻结)

R36 全部是**对冻结语料的离线预测**。以下三句话是它**不支持**的:

1. **不得说「这些建议是正确的」。** 可说的是:
   **通过 H2 成功门的建议, 均与同一来源声明的目标区间内部一致。**
   > 修复版本与用来验证它的区间**来自同一个来源** —— 这是**自洽**, 不是独立正确性证明。
   > 上一版日志写成"GHSA 2,589/2,589 全部正确", 错了两层:
   > ① 2,589 是**声明的修复条数**, 不是 H2 成功数(**2,523**; OSV 是 **126** 不是 131);
   > ② 其中 **`1.2`** 与 **`2026.03.28`** 是 npm 解析不了的版本串, **它们谁都不满足**,
   > 于是在"逃出全部区间"的测试下被当成了"逃掉了" —— 与 §4.2 那条非法版本判据同形,
   > 只是当时没回头查这个探针数。
2. **不得说「真实 lockfile 里没有冲突」** —— 见 §4.2 的更正。
3. **不得说「装上去就一定装得上」。** 依赖解析、peer dependency、传递依赖约束、
   原生模块构建, R36 一概没测。

**这三句只能由真实 GitHub Actions 运行来回答**, 那是另一轮、另一份协议。
**真实运行不取代 H2 主推断, 也不改写 R36** —— 它是外部效度验证。

## 11. 产物必须自带的溯源(R36b 新增)

产物记录三个**内容哈希**, 由门逐一与磁盘比对:

| 字段 | 钉住什么 |
|---|---|
| `protocol_sha256` | 本文件 —— 产出这份结果时所依据的规则 |
| `generator_sha256` | `derive_h2_cicd.py` —— 算出它的那段代码 |
| `gate_sha256` | `Test_h2_cicd.py` —— 验过它的那道门 |

**为什么不写 git commit(与复核意见的一处偏离, 照实记下)**:

- **R23b-F5 已经为此删过一次 `source_commit`** —— 产物必然生成于携带它的那次提交**之前**,
  写进去的只能是父提交, 名字却像是"这份产物所在的提交"。
- 更硬的理由: **把 HEAD 写进产物会直接破坏逐字节复现** ——
  提交之后 `--check` 必然不符, 而 `--check` 是本项目所有产物的基本契约。

**替代做法**: 三个内容哈希提供**精确且不滞后**的溯源; git commit 由**门在运行时打印**、
并记入当轮工作日志。**要恢复该字段, 必须同时把 `--check` 的比对口径改成排除它,
并说明为何这次可以推翻 R23b-F5。**
